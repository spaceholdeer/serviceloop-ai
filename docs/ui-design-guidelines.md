# ServiceLoop UI 设计规范

这份规范是 ServiceLoop AI 所有前端页面的设计基线，适用于客户前端 `/customer`、
人工客服工作台 `/workspace` 和运营后台 `/operations`。新增页面或重构已有页面时，
应先遵守这里的产品与视觉原则，再根据具体业务补充组件。

## 1. 设计目标

ServiceLoop 的界面要让人感到这是一个可信、克制、可追踪的企业服务产品，而不是套用模板的
通用聊天机器人。

优先级从高到低为：

1. 业务状态清楚；
2. 操作路径直接；
3. 数据与 Agent 行为可追踪；
4. 视觉层级稳定；
5. 装饰只服务于理解。

## 2. 必须避免的“AI 模板感”

下列模式默认禁止，除非它确实解决了明确的业务问题：

- 紫蓝渐变、荧光色和大面积玻璃拟态；
- 在应用内部使用居中的营销式巨型标题；
- 同一屏放置三到四张内容相近、尺寸相同的圆角卡片；
- 用机器人、星光、魔法棒等图标装饰每一个 AI 元素；
- 点阵背景、漂浮光斑和没有信息价值的渐变；
- 所有组件都使用大圆角、强阴影和悬浮动画；
- 为显得“专业”而编造实时率、满意度、节省时间等指标；
- 用英文大写标签代替本应直接说明的中文业务名称；
- 把所有回复都做成对称聊天气泡，隐藏业务来源和执行过程。

## 3. ServiceLoop 视觉语言

### 色彩

| Token | 色值 | 用途 |
| --- | --- | --- |
| `pine-deep` | `#0D2823` | 主导航、关键品牌面 |
| `pine` | `#14352F` | 主要操作、用户消息 |
| `canvas` | `#F2F0E9` | 应用背景 |
| `paper` | `#FBFAF6` | 主工作区 |
| `ink` | `#17231F` | 主文字 |
| `ink-soft` | `#68736E` | 次要信息 |
| `amber` | `#D6A64A` | 等待、需注意状态 |
| `line` | `#D9DDD5` | 分隔与边界 |

颜色承担状态含义。不得仅为装饰随意增加主题色；危险、等待、成功等状态在三个使用端保持一致。

### 字体与层级

- 中文优先使用 `Noto Sans SC`、`PingFang SC` 或系统无衬线字体；
- 英文和数字优先使用 `Manrope`；
- 页面标题左对齐，字重控制在 `500–600`；
- 辅助标签可使用大写英文，但必须短、低对比且有明确分组用途；
- 正文行高不低于 `1.6`，长内容不超过约 `70` 个英文字符宽度。

### 间距、圆角和阴影

- 页面采用 `4 / 8 / 12 / 16 / 24 / 32 / 48 / 64` 的间距序列；
- 普通控件圆角为 `4–8px`，消息或特殊容器最大 `10–12px`；
- 优先用留白、细分隔线和色块建立层级；
- 阴影只用于抽屉、弹层和真正离开页面平面的元素；
- hover 动效以颜色、边界和轻微位移为主，持续时间 `120–220ms`。

## 4. 布局原则

- 采用稳定的左侧服务导航和右侧工作区，不把后台做成营销落地页；
- 主要内容左对齐，并通过栏目标题、序号、表格和分隔线形成节奏；
- 同级操作超过两个时，优先使用列表、工具栏或菜单，而不是等宽卡片墙；
- 桌面端正文应有合理最大宽度，避免内容横跨整块屏幕；
- 移动端导航变为抽屉，双栏内容按业务优先级排列为单栏；
- 页面不得产生非预期横向滚动。

## 5. 业务真实性

界面必须准确表达系统当前真正具备的能力：

- 订单和物流回答应说明来自业务 Service；
- RAG 回答应保留知识检索或问题改写记录；
- AI 转人工后显示等待状态，并明确上下文会随转接包传递；
- 退款和用户明确要求人工时，不把它伪装成 AI 继续处理中；
- 未完成的人工工作台和运营后台不得在客户页面冒充已上线功能；
- 演示数据必须能追溯到种子数据、数据库或明确的 mock，不编造产品指标。

## 6. 核心组件约定

### 导航

- 品牌区保持简洁，一个字标加一个产品名即可；
- 历史服务记录使用扁平列表，当前项用左侧状态线或背景区分；
- 用户身份和服务时间放在导航底部，保持低视觉优先级。

### 对话

- 客户消息可以使用紧凑色块；
- AI 和人工回复优先使用正文排版与左侧标记，不强制套气泡；
- 工具调用统一命名为“系统查询记录”，默认收起，展开后显示每一步状态；
- 转人工使用独立状态块，文案必须说明是否已携带上下文。

### 输入与操作

- 主输入框始终位于当前任务附近；
- 主操作使用深松绿色，禁用态必须有明显对比；
- 快捷问题应呈现为服务入口或示例，不包装成营销卡片；
- 键盘行为和限制信息以次级文字呈现。

## 7. 响应式与可访问性

- 至少验证 `1440×900`、`1280×800`、`390×844` 三种视口；
- 可点击区域不小于约 `40×40px`，纯文字操作除外；
- 所有图标按钮必须有 `aria-label`；
- 正文和背景对比度满足 WCAG AA；
- 不得只依靠颜色表达服务状态；
- 尊重 `prefers-reduced-motion`；
- 键盘可以完成打开导航、选择会话、输入和发送消息。

## 8. 每次前端改动的验收清单

前端设计与打磨优先使用 `$impeccable` 对应命令：新界面先 `shape`，现有界面交付前使用
`polish`，可访问性与响应式问题使用 `audit`。命令不能代替产品判断，最终仍以本规范、真实
业务状态和浏览器检查结果为准。

提交前至少完成以下检查：

- [ ] 页面是否一眼能看出这是 ServiceLoop，而不是通用 AI 模板；
- [ ] 首屏是否明确告诉用户当前能做什么；
- [ ] 空状态、加载状态、错误状态、禁用状态和转人工状态是否完整；
- [ ] Tool、RAG 和人工接管信息是否真实且可追踪；
- [ ] 是否避免了无信息价值的卡片、图标、阴影和渐变；
- [ ] 桌面端和移动端都没有横向滚动、遮挡或文字截断；
- [ ] 关键操作可以通过键盘完成；
- [ ] 前端生产构建通过；
- [ ] 使用真实浏览器完成桌面与移动端视觉检查。
- [ ] Impeccable 检测器没有遗留未说明的警告。

## 9. 维护方式

规范不是静态的品牌文档。每次增加新的页面类型、复杂业务状态或可复用组件时，应同步更新
本文件。若一次实现需要违反某项规则，应在代码评审中说明它解决的具体业务问题，而不是
以“更有科技感”作为理由。
