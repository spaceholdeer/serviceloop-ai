# RAG v1 设计约定

## 在 ServiceLoop 中的位置

ServiceLoop 只保留一套 RAG，实现位于 `backend/app/rag`。正式业务代码只通过
知识服务调用它。独立的 `rag/testui` 入口仅用于在本地测试知识录入和检索。

## 检索流程

```text
中文问题
  -> Dense 精确全量扫描，O(N x 1024)
  -> 预构建 BM25 倒排索引
  -> RRF 排名融合
  -> BAAI/bge-reranker-base 精排
  -> 返回带来源的最相关证据
```

Dense 继续使用精确召回，每次扫描所有生效知识块。v0.1 不迁移到向量数据库，
也不使用 HNSW、IVF、ANN、Qdrant、Milvus、pgvector 或 Elasticsearch。

BM25 的语料统计信息和倒排表只在生效知识发生变化时构建。用户发起检索时，
不会重新分词和构建整个语料库。

## 从原 RAG 中移除的内容

- metadata 硬约束
- 约束头信息
- 约束提取和约束不匹配说明
- 独立的 LLM 答案生成层
- 独立的 MySQL 知识块存储

最终答案由客户服务 Agent 生成。它只能根据检索返回的证据回答；证据不足时应当
转人工，不能猜测。

## 动态知识更新

运营人员添加或修改知识时不设置额外审核步骤。每次修改都会生成新的知识版本。
系统对新内容进行分块和向量化，并在不影响当前检索的情况下构建完整的 Dense 与
BM25 索引快照。只有全部构建成功后，新快照才会一次性切换为生效版本。

当前 RAG 测试页面先把知识保存在内存中，以便在数据中台完成前验证上述流程。
下一阶段会使用持久化的 `knowledge_documents`、`knowledge_versions` 和
`knowledge_chunks` 数据表，替换临时的内存字典。

v0.1 不预置业务知识。真实商品和服务资料后续单独整理录入。

## 语言支持

知识标题、知识正文和检索问题同时支持中文和英文，不设置语言拦截规则。当前业务知识
主要是中文，因此中文分词和中文检索效果是第一版的重点；商品型号、订单号和英文术语
可以直接保留，纯英文知识与纯英文问题也可以正常进入检索流程。
